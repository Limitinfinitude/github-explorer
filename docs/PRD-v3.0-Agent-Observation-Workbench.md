# GitHub Explorer PRD v3.0 — Agent 观测与实验工作台

> 日期：2026-08-20（Asia/Shanghai）
> 状态：方向评审稿（替代 PRD v2.0 的「通用操作 Agent」定位）
> 代码基线：`src/` 当前实现（流式、事件溯源、证据仲裁、多模型、观测指标已具备）

## 1. 战略判断：为什么必须换定位

### 1.1 泛化 harness 定位不可行

Claude Code、opencode、Codex、deepseek-harness、ZCode 的竞争方式是：**通用智能 + 可加装插件/Skill 生态**。它们的护城河是模型调用质量、Agent 编排成熟度、插件市场网络效应。在这个维度上做「更强的通用 Agent」是跟随战，没有差异化空间。

### 1.2 「GitHub 项目」定位也被覆盖

主流 harness 为了沙箱构造，一个工作区就是一个项目；GitHub 互通（克隆、推送、Issue、PR）、项目分析、依赖安装都是标配能力。把「跑通 GitHub 项目」作为定位，等于在别人的默认能力上竞争。

### 1.3 真正空缺的位置

主流 harness 全部是**产出导向**：把代码写好、把任务做完。它们的过程（模型怎么想、怎么调用工具、失败怎么恢复、证据是否可靠）是黑盒或次要信息。

**空缺：把 Agent 的一次执行变成可审计、可回放、可对比、可复现的实验数据。**

这正是本项目的既有积累所在：完整事件溯源（SQLite + sequence 回放）、结构化证据账本、不误报完成的终态仲裁、多模型配置、任务级指标快照、结构化评测报告。**已有底座，缺的是产品化收敛。**

## 2. 产品定位

> **GitHub Explorer 是 Windows 本地优先的 Agent 行为观测与实验工作台：把任意 GitHub 项目作为实验材料，让 Agent（可切换模型/配置）在受控工作区执行任务，并把执行全过程沉淀为可回放、可审计、可对比、可复现的实验数据。**

一句话：**主流 harness 卖「结果」，我们卖「过程的数据」。**

实验材料（GitHub 项目）只是载体，不是产品；产品是「Agent 行为的事实记录 + 对比 + 复现」。

## 3. 目标用户

| 用户 | 需求 | 产品入口 |
|---|---|---|
| Agent 开发者/研究者 | 对比模型、工具、prompt、配置对行为的影响；观察失败与恢复 | 对比评测、任务回放、失败模式 |

## 4. 核心概念

### 4.1 实验（Experiment）

一次**受控的 Agent 执行** = 实验材料（GitHub 仓库）+ 任务描述 + 模型/配置快照 + 工作区。实验产出：
- 完整事件流（append-only，可回放）
- 证据账本（文件、验证、进程、HTTP，可交叉验证）
- 指标快照（token、延迟、轮次、恢复率、证据覆盖、终态）
- 终态仲裁结论（completed / incomplete / failed + 原因）

### 4.2 回放（Replay）

事件流按时间轴播放（思考 → 文字 → 工具调用 → 证据 → 终态），支持倍速与跳转。**重放与当时执行完全一致，因为事件是唯一事实源。**

### 4.3 对比（Comparison）

同一实验材料 + 同一任务，在 N 个模型/配置下各跑一次，并排对比：终态、token、延迟、工具轮次、失败恢复次数、证据质量、成本。

### 4.4 失败模式库（Failure Catalog）

自动识别并沉淀高频失败模式（端口冲突、venv 缺失、模型截断、schema 错误、恢复耗尽），成为 Agent 的诊断知识与评测基线。

## 5. 核心场景（用户旅程）

1. 用户导入一个 GitHub 仓库（或本地目录）作为实验材料。
2. 用户选择任务模板（体检/搭建/跑通/二改/自定义）与模型配置。
3. Agent 在隔离工作区执行；用户实时看到流式输出、思考、工具调用。
4. 执行结束：终态 + 证据 + 指标，生成实验卡片。
5. 用户可回放该实验、对比另一个模型跑同一任务、或把该任务加入回归套件。
6. 导出实验报告（Markdown/HTML）。

## 8. 非目标

- 不做通用编码助手（Claude Code 领域）。
- 不做「跑通任意 GitHub 项目」承诺（被沙箱 harness 覆盖）；项目跑不通时提供诊断与证据。
- 不做插件/Skill 生态竞争。
- 不做多 Agent 并行、远程执行、云沙箱、公网多用户。
- 不做 ISSUE 自动修复、自动发布。
- 安全维持本地 loopback + 工作区边界 + 审批。

## 9. 成功指标

### 用户旅程
- 从导入仓库到完成第一次受控实验的时间。
- 同任务双模型对比的完整度（终态/证据/指标齐全）。
- 一次执行能否被完整回放（事件覆盖率 100%）。
- 失败任务能否给出失败模式归类。

### Harness 质量（沿用并强化）
- False completion：0；无证据不报完成。
- 证据无效率 < 1%；完成需求证据覆盖 100%。
- 事件回放与实时一致（sequence 完整）。

## 10. 路线图（从现状到定位）

### P1 — 实验化收敛（对齐定位的最小闭环）
1. 任务 = 实验：启动任务时快照模型/协议/参数，任务详情展示「实验卡片」（材料 + 任务 + 配置 + 终态 + 指标）。
2. 任务回放视图：事件时间轴回放（2x/5x 倍速、跳转），复用现有 sequence。
3. 报告导出：项目/任务 → Markdown/HTML 报告（兑现 PRODUCT.md 承诺）。

### P2 — 对比评测
4. 对比编排：同一任务在 N 个模型下串行跑，并排对比（终态/token/延迟/轮次/恢复/证据）。
5. 指标归一化：统一 token 计费口径、延迟口径、证据质量打分。
6. 回归套件：把任务固化为可反复执行的评测集。

### P3 — 失败模式与画像
7. 失败模式识别：从事件流自动归类（端口冲突/venv/截断/schema/恢复耗尽）。
8. 项目画像：跨实验聚合项目的阶段、事实、已知失败，供新会话直接使用。

### P4 — 可复现与审计
9. 确定性重放：配置快照 + 固定参数 + 事件驱动，同任务可复现执行。
10. 证据交叉验证：进程 PID 归属、文件哈希、HTTP 响应签名。

## 11. 开放问题

3. **评测的「标准答案」**：终态 + 证据是否足够，还是需要人工标注期望结果？
