# Agent 评测方法论参考与融合方案

> 日期：2026-08-21
> 目的：对照成熟 Agent 评测方案（SWE-bench、Terminal-Bench 等），修正本项目的评测设计。
> 触发：r1/r4/r6 三轮评测暴露「单轮波动大、判定依赖模型自述、验收标准模糊」。

## 1. 成熟方案的方法论要点

### SWE-bench（普林斯顿，代码修复评测）

- 任务来自真实 GitHub issue，判定用仓库自带测试：FAIL_TO_PASS（修复前失败、修复后必须通过）+ PASS_TO_PASS（不能回归的测试）。
- 防数据泄露：按时间分割训练/评测集。
- 局限：只覆盖"修复已知 bug"，不覆盖"理解陌生项目、搭建环境、运行服务"。

### Terminal-Bench（Stanford，终端操作评测）

- 任务 = 终端操作（安装、配置、起服务、排查）。
- 判定 = **可执行断言**：脚本化检查（命令输出、文件状态、服务响应），不依赖模型自述。
- 局限：环境容器化成本高，任务粒度偏单步。

### 对本项目最有价值的三个原则

1. **可执行断言取代自述判定**：completed 必须由确定性断言（服务 200 + 测试通过数）裁决，模型说"验证通过"不算数。
2. **分层验收**：关键验收点（服务能起、HTTP 通）+ 非回归点（测试套件不倒退），对应 SWE-bench 的 FAIL_TO_PASS/PASS_TO_PASS。
3. **失败分类学**：每个失败归类到 环境 / 工具 / harness / 模型 / 任务 五类之一，才能知道该修谁。

## 2. 本项目评测设计的缺口（对照结论）

| 缺口 | 现状 | 改进 |
|---|---|---|
| 验收标准模糊 | TASK_PROMPT 说"体检+环境+运行"，无预定义成功标准 | 每个任务模板带**可执行断言清单**（如 `GET /` 200 + `pytest -q` 通过数 ≥ N） |
| 判定依赖自述+模糊仲裁 | 模型自报"验证通过"，harness 用 verification 痕迹仲裁（fastapi 案例暴露） | 断言通过才 completed；断言结果写入验收证据 |
| 数据泄露 | 10 个项目全是知名仓库（模型训练过） | 任务集加入**冷门/小众项目**（测真实探索能力） |
| 单轮波动 | flask/express 轮次间状态翻转 | 多轮取众数（3 轮 2 胜），在"半数项目断言通过"后再启用 |
| 失败无分类 | 只记 error_kind | 结果记录加 `failure_class`（环境/工具/harness/模型/任务） |

## 3. 融合后的评测流程（v2）

```
1. 任务模板化：每个任务 = 项目 + prompt 模板 + 断言清单（可执行）
2. 运行：Agent 全流程执行（体检/环境/运行），记录完整事件
3. 判定：断言脚本执行 → 通过/失败/部分通过（不依赖模型自述）
4. 分类：失败归因五类（环境/工具/harness/模型/任务）
5. 迭代：harness 缺陷优先修 → 复测同一任务
6. 门槛：≥50% 项目断言通过 → 启用多轮（3 轮 2 胜）正式评测
7. 基线：同任务跑多模型/配置对比（复用现有多模型基础）
```

## 4.5 一手资料：Terminal-Bench 3 任务六准则（2026-08-21 经 7890 代理抓取）

所有任务必须满足：**可验证**（程序化检查，正确解必返回 valid，验证器高效可靠）、
**规定明确**（问题描述完整描述验证器查什么，两个理性人写出等价验证器）、**可解**、
**有正当难度的理由**、**现实价值**、**结果验证**（grading outcomes, not the process）。

其中「**结果验证而非过程**」直接修正本项目的终态仲裁：失败痕迹（过程）不应作为
终态二元判据——判定看结果断言（验收点通过），失败痕迹降级为诊断信息。

## 4.6 判定分级设计（平衡支点，对应评审共识）

二元 completed/incomplete 不合理：成熟 harness 也会留失败痕迹，宿主机/网络等变量
不可完全掌控。判定改为**结果优先 + 分级**：

| 级别 | 判定 | 依据 |
|---|---|---|
| passed | 核心验收断言全部通过 | 断言结果（服务 200 / 测试通过数） |
| passed_with_issues | 断言通过，但过程有失败痕迹（被覆盖/环境类） | 断言 + 失败分类 |
| partial | 部分断言通过 | 断言覆盖度 |
| failed | 核心断言失败 | 断言结果 |

- **失败痕迹降级为诊断**：按 环境/工具/harness/模型/任务 五类记录，用于迭代修复，不参与终态二元判定（fastapi「先失败后成功」即 passed_with_issues）。
- **标准变量（环境基线）**：评测前记录并归一化——端口占用清理、模型参数快照、代理/网络状态、系统负载；跨轮可比性依赖基线一致。
