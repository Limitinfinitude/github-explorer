# Agent 记忆系统总体验收报告

## 一、验收结论

当前记忆系统已经达到本阶段设定的**核心功能预期**，可以进入真实本地任务测试。

它已经不再是“把聊天记录全部塞进模型上下文”的简单方案，而是形成了六层相互独立、可以追溯的记忆结构：项目指令、任务工作记忆、执行事件、会话历史、项目长期事实和任务环境快照。

需要准确区分两个结论：

- **核心 Agent 记忆链路：已达标。** 已经能够跨轮次保留任务事实、跨任务检索项目经验，并避免工作区串线和密钥进入记忆。
- **长期运行的产品化成熟度：部分达标。** 还需要经过真实任务积累，才能确定保留周期、检索质量、管理界面和是否需要向量检索。

因此，当前版本适合进入实际使用和观察阶段，但不能表述为已经完全达到 Claude Code 或 Codex 的全部成熟能力。

## 二、原始问题

改造前主要存在以下问题：

1. 上下文超过预算后直接删除最旧消息，模型会遗忘早期决策、失败原因和验证结果。
2. 项目规则、聊天历史、工具结果和长期知识之间没有清晰边界。
3. 工具、文件变更和任务状态分散在多张表中，无法按真实执行顺序回放。
4. 浏览器 `localStorage` 和后端 SQLite 分别保存会话，刷新或更换环境后可能出现两套历史。
5. 不同工作区之间没有长期事实检索层，容易重复探索，也存在未来目录串线风险。
6. 任务没有固定记录使用的模型、工作区、Git 分支和起始提交，难以复现。

## 三、当前整体架构

### 1. 指令记忆

相关实现：`src/agent/runtime/instructions.py`

- 支持用户级、项目根目录和子目录的分层 `AGENTS.md`。
- 同目录 `AGENTS.override.md` 可以覆盖普通规则。
- 项目指令严格限制在当前 workspace root 内，不向父目录越界查找。
- 指令总预算为 32 KiB，预算不足时优先保留更具体目录的规则。
- 无法读取或不是合法 UTF-8 的文件会记录 warning，但不会中断任务。

这一层解决“Agent 在当前项目应该遵守什么规则”，它不属于聊天历史，也不会作为长期项目事实保存。

### 2. 任务工作记忆

相关实现：`src/agent/runtime/compaction.py`

- 模型上下文上限保持为 128K，并为输出预留预算。
- 超过输入预算后生成结构化 `ContextHandoff`，不再只是删除最旧消息。
- 交接内容包括目标、进度、决策、约束、工作目录、变更文件、验证、失败、待办和引用。
- 最新用户请求始终保留。
- SQLite 中的完整原始任务消息不会因为压缩而删除。
- API Key、Token、Authorization 和密码等字段会在交接内容中脱敏。

这一层解决“长任务进行到一半时，下一轮模型还需要记住什么”。

### 3. Thread Event Store

相关实现：`src/agent/memory.py`、`src/agent/runtime/runtime.py`

- 新增顺序事件表 `agent_events`。
- 每个 task 使用独立、连续递增的 `sequence`。
- 记录任务开始、计划、工具调用、工具结果、审批、文件变更、进程、验证、错误、上下文压缩和任务结束。
- 事件在 SSE 输出给前端前先写入 SQLite。
- 审批暂停和 resume 继续使用原 task id 和原事件序列。
- 事件 payload 在写入数据库前递归脱敏。
- 原有 `agent_tool_runs` 和 `agent_changesets` 暂时保留为兼容投影。

这一层解决“任务实际发生了什么、按什么顺序发生”。

### 4. 会话记忆

相关实现：`src/agent/memory.py`、`src/web/src/hooks/useChats.ts`、`src/web/src/lib/chatHistory.ts`

- 后端 `conversations` 表作为完成对话的事实来源。
- 前端通过稳定的 `sessionId` 从后端恢复历史。
- 后端返回真实历史时，前端会使用它同步当前聊天。
- `localStorage` 继续作为浏览器缓存和旧版本数据兜底。
- 空后端历史或接口暂时失败时不会清空本地缓存。
- 前端 UI chat id 和后端 session id 保持明确分离。

这一层解决“刷新页面以后还能否恢复正确的对话”。

### 5. 项目长期记忆

相关实现：`src/agent/memory.py`、`src/agent/runtime/runtime.py`

- 新增规范表 `project_memories` 和全文索引 `project_memory_fts`。
- 每条记忆包含工作区、内容、来源类型、来源 id、置信度、验证状态、过期时间和时间戳。
- 使用 SQLite FTS5 检索，不依赖额外向量数据库或原生扩展。
- 检索必须携带准确的 workspace root，避免不同项目之间串线。
- 同一 task 来源采用幂等 upsert，不会反复产生重复事实。
- 自动写入只接受完成任务中的文件变更和验证事实。
- 普通聊天、失败任务和没有变更/验证事实的任务不会写入项目长期记忆。
- 运行时默认只自动召回 `verified` 事实；只有文件变更但未验证的内容保存为 `partial`，不会自动影响后续模型。

这一层解决“同一项目后续任务能否复用以前已经验证过的事实”。

### 6. 可复现快照

相关实现：`src/agent/runtime/runtime.py`、`src/routes_agent.py`

- 每次任务创建时记录模型 ID、协议和 Base URL。
- 模型快照不包含 API Key。
- 保存 workspace root、current path 和项目 profile。
- 保存任务开始时的 Git 分支和 HEAD。
- `task_started` 事件和 `agent_tasks.state_json` 都包含快照。
- 自动生成的项目记忆会携带 Git 分支和基线提交。

这一层解决“这条记忆是在什么项目版本和模型配置下产生”。

## 四、执行链路

一次 Agent 请求现在按以下顺序工作：

1. 根据 session 解析工作区和 current path。
2. 加载本次任务固定的分层项目指令。
3. 捕获模型、工作区和 Git 基线快照。
4. 在当前 workspace 内检索与用户请求相关的 verified 项目记忆。
5. 创建任务状态并写入 `task_started` 事件。
6. 调用模型并执行工具，所有结构化事件按顺序持久化。
7. 上下文超过预算时生成 `ContextHandoff`，完整历史仍保留在 SQLite。
8. 任务完成后，将确定性文件和验证事实写入项目记忆。
9. 前端通过 SSE 展示当前任务，通过 Activity 和任务接口回看历史事件。

## 六、安全与隔离判断

当前实现已经具备必要的基础安全边界：

- 服务只监听 `127.0.0.1:7788`，不监听 `0.0.0.0`。
- 工作目录由 WorkspaceManager 限制，路径不能越过 workspace root。
- 项目记忆按 workspace root 隔离。
- 指令加载不会沿父目录无限向上读取。
- 事件、上下文交接和项目记忆都有敏感信息脱敏。
- 模型快照只接受 id、protocol 和 base_url，不接收 key。

但这不是正式安全审计。未来新增工具参数、第三方协议或新的日志字段时，仍必须继续执行密钥扫描和脱敏测试。

## 八、尚未完成但不阻塞当前使用的项目

### 1. Retention 与归档

事件和长期记忆目前没有自动清理策略。应先记录真实数据库增长速度，再决定按天数、任务数或容量归档。

### 2. 记忆管理界面

当前已有只读搜索 API、来源、验证状态和置信度，但还没有面向用户的编辑、降权、删除和固定记忆操作。删除语义需要避免误删任务审计事实。

### 3. 检索效果指标

当前没有记录每次召回是否真正被后续任务使用，也没有命中、误命中和零结果统计。没有这些数据时无法客观判断是否需要 embeddings。

### 4. Git 边缘情况

普通分支、detached HEAD 和 gitdir 文件已覆盖；仅存在于 packed-refs 中的分支提交还需要补充解析。

### 5. 多标签页实时同步

SQLite 会话事实不会丢失，但不同浏览器标签页之间尚未通过 BroadcastChannel 或事件订阅实时同步 UI 缓存。

## 九、是否达到预期

**结论：核心预期已经达到，产品化长期运营预期尚未全部达到。**

如果验收标准是“Agent 能在本地项目中稳定记住规则、长任务状态、执行事实、历史会话和已验证项目知识，并且可以追溯来源且不跨工作区串线”，当前版本已经达标。

如果验收标准是“具备成熟商业产品的记忆管理、自动归档、检索评测、所有 Git 边缘兼容和向量语义召回”，当前版本还没有完全达标。这些能力应建立在真实使用数据上继续实施，而不是现在无指标地增加复杂度。

建议当前进入实际测试阶段，重点收集以下数据：

1. FTS5 检索的命中、误命中和零结果次数。
2. `ContextHandoff` 是否遗漏早期决策或失败原因。
3. `agent_events` 和 `project_memories` 每周增长体积。
4. partial 与 verified 记忆的实际比例。
5. 用户是否需要手工固定、修正或删除项目记忆。

这些数据将直接决定下一阶段优先实现 retention、管理 UI、packed-refs 兼容还是 embeddings。
