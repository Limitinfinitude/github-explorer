# 批量项目评测记录（2026-08-20）

> 目的：用真实 GitHub 项目实测 harness 的「体检 + 环境 + 运行验收」全流程能力，
> 定位失败模式，作为优化依据与面试实证材料。

## 评测设计

- **项目**：10 个知名开源项目，浅克隆到 `D:\GE-eval-projects`，语言分布 Python×4 / JS×2 / TS×2 / Go×2
  - Python: fastapi, flask, rich, pytest
  - JS: express, axios
  - TS: zod, vitest
  - Go: gin, cobra
- **任务**：全流程 prompt（阶段1 体检 → 阶段2 项目内建环境装依赖 → 阶段3 服务/测试运行验收）
- **模型**：deepseek-v4-flash（opencode.ai 网关），thinking_effort=on（普通思考）
- **隔离**：每项目独立 session + 独立工作区；项目内建 `.venv`，不污染系统环境
- **干净重跑**（r2 起）：git clean/reset 恢复初始克隆状态 + 换新 session + 清项目记忆
- **批跑**：`D:\GE-eval-projects\run_eval.py`，串行，结果 JSONL

### 第一轮暴露的问题

1. **轮次预算不足（主因）**：7 个 incomplete 全部 rounds=13 = max_rounds 12 + 收尾。全流程任务 12 轮不够。
   → 修复：生产配置 `max_rounds=24`。
2. **finalization 空回复**：轮次耗尽后收尾模型返回空 → 用户看到「模型未返回最终说明」。
   → 修复：收尾空回复时带用户问题重试一次。
3. **审批挂起**：cobra 触发高风险操作等待审批，评测脚本未处理。
   → 修复：脚本加自动批准（评测环境）。
4. **流式 usage 缺失**：OpenAI 流式 chunk 不带 usage，express/axios/cobra tokens=0。
   → 修复：收集流式最后 chunk 的 usage。
5. **search_text 路径报错**：对不存在的路径报 tool_error（4 次）——待优化。

### 有价值的真实诊断（失败模式种子）

- **pytest**：Agent 自主定位「浅克隆无 git tag → setuptools-scm 版本解析失败 → 触发项目 minversion 守卫」，
  并给出修复方向（fallback_version）——判断正确，轮次耗尽未修完。

## 持续失败项目逆向溯源（2026-08-21，观测链定位）

用事件链（DB agent_events 的 tool_call/tool_result 关联）逐个还原失败路径，按五类归因：

### fastapi — harness 类（已修复）

8000 端口冲突 → 换 8011 → 首次相对路径启动失败 → wait_http 超时（记录失败）→
二次绝对路径启动成功 → HTTP 200 + 验收全过 → **但旧失败记录判 incomplete**。
修复：终态仲裁"同类验证最后状态"判定（失败被后续成功覆盖）。

### rich — harness 类（已修复）

最终测试全过（pytest ✓、verify_project ✓），但**无关的 search_text 失败**（poetry.lock
路径）判 incomplete。修复：**结果优先**——有成功结果证据时，过程失败降级为诊断不判死
（Terminal-Bench「grading outcomes, not the process」）；无验证证据时保持严格防误报。

### pytest — harness 类（部分修复）

setuptools-scm 版本问题被 Agent 用环境变量绕过（行为正确），测试实际通过；
但 `timeout>600` 被 schema 拒（模型不知上限）、`Start-Sleep 180` 被工具超时误杀、
轮次 24 耗尽在收尾前。修复：工具执行超时 180→300s。schema 上限提示与轮次预算待评估。

### gin — 环境类（待评测侧处理）

GOPATH/GOMODCACHE 隔离正确，但 go 模块下载/构建反复退出码 1（网络/代理/go proxy），
模型反复重试同命令。评测环境基线需统一 go proxy；模型恢复策略待观察。

### 终态仲裁 v2 总结

| 条件 | 结果 |
|---|---|
| 有成功结果证据 + 无验证失败 | 过程失败降级 → completed（passed_with_issues 语义） |

| 无任何验证证据 | 严格判定（unrecovered 判死） |

## gin 环境基线深挖结论（2026-08-21）

手动复现 gin 构建失败，逐层排除：

1. **proxy.golang.org 被墙**（000）、sum.golang.org 被墙（000）、goproxy.cn 通（200）、GitHub 直连通（302）。
2. GOPROXY=goproxy.cn + GONOSUMDB=* 后 `go get`/`go mod download` 正常、模块缓存完整。
3. **go mod graph 包含全部依赖节点、缓存有完整模块、go.mod 有 require，但 `go build` 仍报
   "no required module provides package"**——go 1.26.7 工具链的模块图解析 bug（图与 build 不一致）。
   换 proxy、清空缓存（rm/PowerShell 强制删）均无法解决。

**结论**：gin 的 r6 失败 = 环境/工具链问题（go 1.26.7 模块图 bug + 默认 proxy 被墙），非 harness 问题。
Agent 行为（GOPATH 隔离、换 proxy、清缓存）是正确的，但遇到工具链 bug 无法自行解决。

**评测环境基线（沉淀到脚本 v2）**：
- go 项目：`GOPROXY=direct`（goproxy.cn 的 zip 有损坏风险）、`GONOSUMDB=*`
- 环境快照：评测前记录 go/python/node 版本、proxy 可达性、端口占用
- 已知工具链限制：gin 类 go 1.26 图解析异常记录为 environment/toolchain 分类

### 失败卡点三类（run_command 104 次失败归因）

1. **模型类：shell 方言混用**——`set GOMODCACHE=...`（CMD 语法）vs `$env:`（PowerShell）混用（zk）。
2. **环境类：Python 解释器混乱**——Agent 反复删 .venv、试 C:eat\python39 / D:\Python3.10.9 等多个系统 Python（sclack/openrecall）；AI 重依赖（torch 几 GB）安装超时。
3. **harness 类：修复型任务轮次不足**——链路确认模型能看到完整编译错误（output 1024 字符含 TS2322 详情），但真实应用失败是「修复型」（改代码→编译→再改），24 轮不够。**环境型（装好就行）vs 修复型（改好才行）是核心难度分层**。

### 三类修复（已落地，308 测试通过）

- 系统提示词规则 7：Windows 统一 PowerShell 语法（$env:），禁止 CMD set。
- 系统提示词规则 8：Python 只用 ensure_venv 管理项目 .venv，禁止试系统 Python。
- max_rounds 24→32（生产配置）。
