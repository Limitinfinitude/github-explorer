# 产品定位与 LangGraph 处置决策记录

> 时间：2026-08-14（Asia/Shanghai）

## 遇到了什么

前端升级原计划围绕 Chat、Explore、Activity 和 Settings 做视觉重排，但用户指出首要用户不只是写代码的开发者，还包括寻找项目学习的大学生、研究陌生仓库的开发者，以及只想直接体验项目的小白。若此时直接改 UI，容易把当前“通用本地操作 Agent”的宽泛能力包装成没有差异化的产品。

同时需要确认 LangGraph 是否仍是项目核心。代码审计发现项目存在两套编排路径：新的 `LocalAgentRuntime` 已承载主 SSE Agent 链路；LangGraph 仍被旧 API、setup/confirm、搜索解释和 Swarm 路径直接调用。

## 发现了什么

1. 产品真正的断点是“陌生仓库 -> 可运行 -> 可理解 -> 可二改 -> 可复盘”，不是缺少一个能执行 shell 的聊天框。
2. GitHub、Codespaces、Replit 和 IDE Agent 分别覆盖发现、云端运行或代码修改，但没有把 Windows 本地诊断、运行身份、架构学习、隔离实验和证据记录合成一个闭环。
3. 运行记录和工具流水账对开发者不是噪声，而是测试 Harness、排查假成功、研究模型行为和优化产品的必要数据。正确方案是双层展示：用户摘要默认可读，开发者证据同页展开。
4. LangGraph 的源代码占比很小，但入口影响大。当前 `src` 统计约 349,770 行，直接导入 LangGraph 的文件 9 个、约 1,107 行，约占 0.32%；它不是运行时主链的主要代码量，却仍是高风险兼容边界。

## 分析

直接删除 LangGraph 会同时破坏旧分析 API、环境 setup/confirm、搜索解释和 Swarm；继续让它和 Runtime 并行扩展，则会造成状态、审批、事件和观测事实分裂。最小风险路径是：先保留、隔离、标记 legacy；新能力只进 Runtime；逐个迁移旧入口；最后按调用量和回归结果决定移除或独立插件化。

## 改进计划

### 产品层

- 采用“GitHub 项目可运行性与学习路径工作台”定位。
- 以项目旅程作为主导航：项目库、体检、跑起来、看懂、实验室、记录。
- 保留 Chat 和 Activity，但将完整流水账纳入项目页的开发者证据层。

### 架构层

- `Session Event Store` 作为 Chat、Activity、Acceptance、项目记录和 LangSmith 的唯一事实源。
- `LocalAgentRuntime` 作为新主链，统一 Turn、Step、Tool call、审批、恢复和最终化。
- LangGraph 只作为 legacy compatibility surface，不再新增业务能力。
- 为旧入口增加迁移适配、调用计数和回归测试。

### 验证层

- 初学者、开发者、体验者各设计隔离任务，分别测量从导入到下一步、从导入到运行、从运行到二改的时间和失败轮数。
- 每次任务同时验收用户摘要和开发者证据层，确保“好看”不以丢数据为代价。

## 最终效果

已确认新的产品事实并写入 `PRODUCT.md`。LangGraph 没有被贸然删除，而是形成了有退出条件的迁移路线。前端实现尚未开始，避免在产品定位和编排边界未固定前产生返工。
