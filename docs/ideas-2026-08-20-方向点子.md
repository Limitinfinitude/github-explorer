# GitHub Explorer 方向点子清单

> 日期：2026-08-20
> 背景：已否定「通用 harness」（生态竞争）、「GitHub 项目定位」（沙箱 harness 默认能力）、「过程可观测」（dsh 有轨迹+复盘）、「项目体检」（也是 harness 默认能力）。陷入方向迷茫，参考 pi-agent「简单、从简」哲学。

## 0. 为什么一直找不到方向（诊断）

我们一直在**功能维度**找差异化（观测、评测、体检、回放…），但每个功能都被主流 harness 覆盖或即将覆盖。功能维度的差异化是零和游戏：Claude Code / opencode / dsh 每周都在加功能。

差异化的真正坐标不是「多一个功能」，而是三件事的组合：
1. **用户**：为谁做（而不是为「Agent 开发者」这个模糊人群）
2. **交付物**：一个明确的、有限的产出（而不是一个平台）
3. **不做的事**：砍掉什么（从简哲学）

## 1. 换「交付物」——不卖工具，卖一个明确产出

### 1.1 Agent 失败模式知识库
- 一句话：把大量真实任务里 Agent 的失败（端口冲突、venv 缺失、模型截断、schema 错误、恢复耗尽）自动归类，沉淀成可检索的「项目跑不通原因大全」。
- 给谁：所有用 harness 的人（Claude Code 用户也会遇到同样的失败）。
- 为什么没人做：dsh 的复盘是单次会话回顾；这是**跨项目累积的领域知识**，需要大量真实执行数据——恰好是本项目事件溯源 + 失败恢复统计的天然产出。
- 风险：知识库冷启动难；价值取决于数据量。

### 1.2 可复现实验包（Agent 的 git）
- 一句话：每次 Agent 执行生成一个「实验包」（事件 + 证据 + 配置 + 指标），可导出、分享、回放、对比。像把一次任务变成 commit。
- 给谁：Agent 研究者、评测工程师。
- 为什么没人做：主流 harness 的事件不结构化、不可导出。
- 风险：概念重，用户教育成本高。

### 1.3 项目跑通报告（被否过，但换个形态）
- 一句话：不是「帮你跑」，而是**生成一份可分享的报告**（PDF/Markdown）：这项目能跑吗、依赖树、入口、端口、已知坑。像 Resumake 之于简历。
- 风险：用户已说这是 harness 默认能力。但「报告生成器」作为独立交付物 ≠ harness 的顺带能力——需要判断。

## 2. 换「用户」——不为 Agent 开发者做，为特定人群做

### 2.1 Agent 教学工具
- 一句话：给初学者/学生展示「一个 Agent 如何从零理解并跑通陌生项目」——可回放、可讲解、可布置作业。
- 给谁：教育场景（教师、学生、培训机构）。
- 为什么没人做：Claude Code/dsh 不面向教学；教学需要「过程叙事」而非「结果」。
- 现有积累：完整事件回放 + 流式 + 思考显示 + 项目旅程，全都有。
- 风险：用户可能不想要教育定位。

### 2.2 Agent 配置评估服务
- 一句话：企业场景——「哪个模型+prompt+参数组合最适合你的代码库？」用真实任务集评估并给出报告。
- 给谁：技术团队选型。
- 为什么没人做：需要受控执行 + 对比指标，正是本项目积累。
- 风险：企业级交付（多用户、报告、计费）超出当前范围；与 127.0.0.1 本地定位冲突。

## 3. 换「形态」——不是 harness，是别的

### 3.1 离线隐私优先的本地 AI 工具箱
- 一句话：纯本地、无云、BYOK、数据不出机器。所有 harness 都在向云端/协作走，隐私是反方向。
- 给谁：隐私敏感场景（公司代码、研究数据）。
- 现有积累：127.0.0.1 设计、本地 SQLite、BYOK 多模型——已经是这个形态。
- 风险：「本地优先」是属性不是定位，无法单独立住。

### 3.2 垂直领域专项
- 一句话：不做通用，只做「数据分析项目」「Python 学习项目」或「前端模板项目」的深度跑通器——针对该领域优化（依赖、环境、常见坑）。
- 风险：垂直领域市场小；且垂直化后仍是 harness 能力子集。

## 4. 从简哲学——参考 pi-agent：砍到一句话

### 4.1 一个输入框 + 一个输出
- 产品 = 粘贴 GitHub 链接 → 得到一份「能不能跑 + 为什么 + 怎么跑」的结论。
- 砍掉：chat、工具调用可视化、评测、回放、多模型对比——全部做成「高级模式」藏在设置里，主界面只有一个输入框。
- 像 pi-agent：初衷简单、场景单一、做到极致。
- 风险：功能已多，砍掉需要决心；且「跑通项目」仍是 harness 默认能力，除非报告本身有独特价值（如跨项目跑通率数据）。

## 5. 推荐

### 首选：1.1 失败模式知识库 + 报告交付物
把项目现有的「事件溯源 + 失败恢复统计 + 终态仲裁」沉淀成**别人没有的数据资产**（跨项目的跑通/失败知识），交付物是报告而非工具。主流 harness 不积累这个，dsh 的复盘是单次的。

### 次选：4.1 从简（一个输入框一个输出）
如果数据资产路线觉得重，就走 pi-agent 路线：**砍功能，留一个场景**。「粘贴链接 → 结论报告」，其余全藏起来。这是哲学选择，不是功能选择。

### 兜底建议
如果以上都不满意，先做一件事：**停掉功能开发，用现有能力跑 50 个真实 GitHub 项目，统计跑通率/失败模式分布**。数据会告诉我们哪个定位成立——「跑通率最高的 20 个失败原因」本身就是产品（1.1 的种子数据）。
